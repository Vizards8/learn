# AV号与BV号转换设计文档

## 一、问题背景

类似短网址服务需要将长URL映射为短字符串，B站需要将数字ID(AV号)转换为更友好的字符串ID(BV号)。

**核心需求：**
- 将纯数字ID(如`av170001`)转为固定长度的字符串ID(如`BV17x411w7KC`)
- 双向可逆转换，无信息丢失
- 美化展示效果，避免数字过长暴露业务规模
- 一定程度的ID混淆，增加反爬难度

## 二、设计方案

### 2.1 整体思路

```
AV → BV:  数字ID → [混淆] → [进制编码] → [位置打乱] → 字符串ID
BV → AV:  字符串ID → [位置还原] → [进制解码] → [反混淆] → 数字ID
```

**类比短网址：**
- 短网址: 数据库ID → Base62编码 → 短码
- BV号: AV号 → 混淆+Base58编码+位置交换 → BV号

### 2.2 关键设计决策

#### (1) 为什么用58进制？

```go
_base = 58
_alphabet = "FcwAPNKTMug3GV5Lj7EJnHpWsx4tb8haYeviqBz6rkCy12mUSDQX9RdoZf"
```

- **去除易混淆字符**: 避开 `0/O`, `1/I/l` 等
- **足够的编码空间**: 58^9 >> 2^51，空间充裕
- **自定义字母表**: 打乱顺序，非标准Base58，增加逆向成本

#### (2) 为什么是9位编码？

**核心数学计算：**

```
需要表示的最大值: 2^52 - 1 (加标志位后的52位数)
58进制能力:
  - 58^8 = 2.2×10^15 < 2^52 (不够)
  - 58^9 = 1.28×10^17 > 2^52 (足够)

计算公式: log₅₈(2^52) = 52 × log(2) / log(58) ≈ 8.87
向上取整: 9位
```

**为什么不用8位或10位？**
- 8位: `58^8 < 2^52`，无法表示所有ID，会溢出
- 10位: `58^10 >> 2^52`，空间浪费，字符串过长
- 9位: 刚好够用，`58^9 / 2^52 ≈ 28倍`空间余量，平衡最优

**模58运算的本质：**
```go
for tmp != 0 {
    result = alphabet[tmp % 58] + result  // 取余数对应字符
    tmp = tmp / 58                        // 进位继续
}
```
这是标准进制转换算法，类似十进制转二进制要"模2"。

#### (3) 如何保证固定长度？

```go
tmp := ((1 << 51) | avid) ^ _xorcode
```

**问题**: 直接编码会导致小ID生成短字符串(如av1 → "BV1Fc")

**解决**: 在第51位设置标志位
- `avid=1` → `tmp = 0b1000...0001` (52位)
- `avid=2^51-1` → `tmp = 0b1111...1111` (52位)
- 确保所有avid编码后都是52位二进制，转58进制后长度统一为9位

#### (5) 为什么要异或混淆？

```go
_xorcode = 23442827791579

// 编码
tmp = ((1<<51) | avid) ^ _xorcode

// 解码
avid = (tmpNum & _maskcode) ^ _xorcode
```

**目的**:
- 打破ID的连续性(av1和av2的BV号看起来无关)
- 利用XOR自反性: `A ^ B ^ B = A`，保证可逆
- 低成本的混淆方案，无需查表

#### (6) 为什么要字符位置交换？

```go
swap(ids[0], ids[6])  // 第0位 ↔ 第6位
swap(ids[1], ids[4])  // 第1位 ↔ 第4位
```

**目的**:
- 二次混淆，进一步打破规律
- 即使知道alphabet，也难以直接暴力破解
- 交换模式是硬编码的，只有掌握规则才能逆推

## 三、核心实现

### 3.1 AV → BV 转换流程

```go
func AvToBv(avid int64) (string, error) {
    // 1. 边界检查
    if avid < 1 || avid >= 2^51 { return error }

    // 2. 添加标志位 + 异或混淆
    tmp := ((1 << 51) | avid) ^ 23442827791579

    // 3. 58进制编码
    result := ""
    for tmp != 0 {
        result = alphabet[tmp % 58] + result
        tmp /= 58
    }

    // 4. 字符位置交换
    swap(result[0], result[6])
    swap(result[1], result[4])

    // 5. 添加前缀
    return "BV1" + result
}
```

### 3.2 BV → AV 转换流程

```go
func BvToAv(bvid string) (int64, error) {
    // 1. 去前缀 "BV1" 或 "1"
    bvid = stripPrefix(bvid)

    // 2. 位置逆交换(顺序相反)
    swap(bvid[1], bvid[4])
    swap(bvid[0], bvid[6])

    // 3. 58进制解码
    num := 0
    for char in bvid {
        idx := indexOf(alphabet, char)
        num = num * 58 + idx
    }

    // 4. 去标志位 + 异或还原
    avid := (num & 0x1FFFFFFFFFFFF) ^ 23442827791579

    return avid
}
```

## 四、技术亮点

### 4.1 与短网址设计的对比

| 维度 | 短网址 | BV号 |
|------|--------|------|
| 编码方式 | Base62 | Base58(自定义) |
| 长度 | 可变(6-8位) | 固定(12位含前缀) |
| 混淆 | 可选(hash) | 内置(XOR+位置交换) |
| 存储 | 需要数据库 | 无需存储(纯算法) |
| 可逆性 | 单向(需查表) | 双向(算法可逆) |

### 4.2 设计优势

1. **零存储开销**: 纯算法转换，无需维护映射表
2. **高性能**: O(1)时间复杂度，无IO操作
3. **强一致性**: 同一avid永远生成相同bvid
4. **适度混淆**: 既保护业务数据，又不影响性能

### 4.3 ID容量

```
理论容量: 2^51 = 2,251,799,813,685,248 (2千万亿+)
实际使用: B站视频量级在亿级别，空间充足
编码后长度: 固定9个字符(+ "BV1" 前缀 = 12字符)
```

Step4: 加前缀 → "BV17x411w7KC"

## 六、面试核心问题

**Q1: 为什么不直接用Base62编码？**
- 需要去除易混淆字符，提升用户体验
- 自定义字母表增加逆向难度
- 58进制编码空间已足够(58^9 > 2^51)

**Q2: XOR混淆安全吗？**
- 不是为了绝对安全，是为了适度混淆
- 防止简单的ID遍历和规律性分析
- 配合位置交换，增加破解成本
- 真正的安全依赖后端权限控制

**Q3: 如何保证不重复？**
- 一一映射关系，由数学保证
- avid唯一 → 经过确定性算法 → bvid唯一
- 类似哈希但可逆，无碰撞风险

**Q4: 能支持多少ID？**
- 51位二进制: 2^51 ≈ 2.25千万亿
- 远超业务需求(当前B站视频数亿级)
- 未来不够可升级算法(如增加标志位到52位)

**Q5: 性能瓶颈在哪？**
- CPU密集型操作(位运算+进制转换)
- 单次转换微秒级，可轻松支持高并发
- 无IO操作，适合缓存在应用层

## 七、扩展思考

### 7.1 如果需要更高安全性？
- 引入时间戳混淆(但会牺牲幂等性)
- 使用加密算法(AES加密avid，但性能下降)
- 分段编码(不同业务用不同xorcode)

### 7.2 如果需要更短的ID？
- 减少标志位(牺牲长度统一性)
- 使用Base62(增加字符集)
- 压缩编码(但增加复杂度)

### 7.3 横向扩展
- 短网址: 需要分布式ID生成(Snowflake等)
- BV号: 已有avid体系，直接转换即可
- 其他场景: 订单号混淆、用户ID美化等

#### 3.2 编码长度
